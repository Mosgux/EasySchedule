# Research Phase: 多人时间协商可视化系统

**Purpose**: 技术选型研究和最佳实践分析
**Created**: 2025-01-13
**Status**: Complete

## 技术栈研究决策

### 前端技术栈

**React 18 + Vite + TypeScript**

- **决策**: 选择React 18 + Vite作为前端框架
- **理由**:
  - React 18的并发特性适合大量DOM/SVG元素渲染
  - Vite提供极快的开发体验和构建速度
  - TypeScript确保类型安全，前后端类型一致性
- **替代方案考虑**: Vue 3 + Vite，但React生态更丰富

**Tailwind CSS**

- **决策**: 选择Tailwind CSS作为UI框架
- **理由**: 符合宪章要求，提供统一的设计系统
- **替代方案考虑**: Styled Components，但Tailwind更符合团队技能

**Day.js**

- **决策**: 选择Day.js处理时间和时区
- **理由**: 轻量级（2KB），API简洁，支持时区和本地化
- **替代方案考虑**: Moment.js，但体积过大

**TanStack Query**

- **决策**: 选择TanStack Query管理服务端状态
- **理由**: 自动缓存、后台更新、乐观更新支持
- **替代方案考虑**: SWR，但TanStack Query功能更全面

### 后端技术栈

**Node.js 18.19.0 + Express + TypeScript**

- **决策**: 选择Node.js + Express作为后端框架
- **理由**:
  - Node.js 18 LTS稳定且性能优秀
  - Express生态成熟，中间件丰富
  - TypeScript确保类型安全
- **替代方案考虑**: Fastify，但Express更广泛使用

**SQLite + Prisma**

- **决策**: 选择SQLite作为数据库，Prisma作为ORM
- **理由**:
  - SQLite单文件部署，适合小规模应用
  - Prisma提供类型安全的数据库操作
  - 迁移管理简单，支持版本控制
- **替代方案考虑**: PostgreSQL，但SQLite更简单

**nanoid**

- **决策**: 选择nanoid生成分享链接ID
- **理由**: 生成难以枚举的URL安全ID，体积小
- **替代方案考虑**: UUID，但nanoid更短且更安全

**node-cron + winston**

- **决策**: 选择node-cron处理定时任务，winston记录日志
- **理由**:
  - node-cron轻量且功能完整
  - winston支持文件滚动和结构化日志
- **替代方案考虑**: bull队列，但对于简单清理任务node-cron足够

### 性能优化策略

**前端渲染优化**

- 使用React.memo和useMemo优化组件重渲染
- 实现虚拟化滚动处理大量日历数据
- 使用CSS Grid和SVG优化日历视图渲染
- 代码分割和懒加载减少初始加载体积

**后端性能优化**

- SQLite启用WAL模式提升并发性能
- 实现Redis缓存层减少数据库查询
- 使用连接池管理数据库连接
- 实现API响应缓存和压缩

### 安全性设计

**轻量级安全策略**

- 输入验证和SQL注入防护（Prisma原生支持）
- XSS防护和内容安全策略
- 基础的请求限速防止滥用
- 难以枚举的分享链接ID

### 部署架构

**NGINX反向代理**

- 前端静态文件通过NGINX直接提供
- API请求代理到后端Express服务器
- 启用Gzip压缩和缓存策略
- 支持HTTPS和安全头部

## 技术风险评估

### 高风险项

- **SQLite并发限制**: 在50人同时访问时可能出现性能瓶颈
  - **缓解措施**: 启用WAL模式，实现Redis缓存，优化查询

### 中风险项

- **前端性能**: 大量SVG元素可能影响渲染性能
  - **缓解措施**: 虚拟化渲染，React 18并发特性，智能重渲染

### 低风险项

- **部署复杂性**: Windows Server 2012 R2环境较旧
  - **缓解措施**: 使用Docker容器化，简化部署依赖

## 性能基准

根据宪章要求和规格指标：

- **页面加载时间**: <3秒（目标50人并发）
- **日历渲染时间**: <1秒（30名参与者数据）
- **API响应时间**: <500ms（99%请求）
- **数据库查询**: <100ms（优化后）

## 下一步行动

1. **Phase 1**: 设计数据模型和API契约
2. **实现核心功能**: 时间表创建、参与者填写、可视化展示
3. **性能优化**: 实现缓存和渲染优化
4. **安全加固**: 实现输入验证和限速
5. **部署准备**: 配置NGINX和Docker环境

## 研究结论

所选技术栈完全符合EasySchedule宪章要求，能够满足20-50人规模的时间协商需求。React 18 + Express + SQLite的组合提供了良好的开发体验和部署简单性，同时通过适当的优化策略能够满足性能要求。

所有技术选择都遵循"简洁第一"和"够用就好"的原则，避免过度设计，专注于核心功能的实现。
